## Helm baseline

1. `Chart.yaml` declares `apiVersion: v2` and a real semver `version` — `helm lint` fails outright without one (confirmed against a real binary: a `Chart.yaml` missing `version` produces `[ERROR] Chart.yaml: version is required` and a non-zero exit), so a finding here means the chart itself does not build, not just a style preference.
2. `appVersion` is set and reflects the application image actually deployed, not the chart's own packaging version — the two version numbers mean different things and drift independently.
3. A `values.schema.json` alongside `values.yaml` is recommended for any chart a team other than the chart's own author configures — it turns a bad override into a `helm template`/`helm lint` failure instead of a runtime one.
4. No literal secret value ever appears in `values.yaml` or a template's own default — a value meant to be secret is a `Secret` reference (`envFrom`/`secretKeyRef`), the same rule `infra/kubernetes/guidance/baseline.md` rule 6 already states for a raw manifest, applying identically here.
5. Every rendered resource carries Helm's own two documented recommended labels, `helm.sh/chart` and `app.kubernetes.io/managed-by` (https://helm.sh/docs/chart_best_practices/labels/) — `infra.helm.policy`'s own rego enforces this against the rendering. `infra/kubernetes/guidance/baseline.md` rule 2's own `app.kubernetes.io/name` requirement still applies on top of these, not instead of them — the three labels serve different lookups (this chart's own identity, its packaging, and its own instance's release).
6. Subchart (`charts/`) versions are pinned exactly in `Chart.yaml`'s `dependencies[]`, never a floating range — a subchart is vendored content this repository's own review controls, not something that should silently change between two runs of `helm dependency update`.
7. `infra.helm.policy` (conftest) runs with `input: "render"`, never `"source"` — a chart's own `templates/*.yaml` files are not valid YAML before rendering (Go template syntax, confirmed against a real `conftest` binary to abort the whole invocation rather than report a per-file finding), so a policy needing genuine per-resource detail must run against `helm template`'s own output, exactly like `infra/kubernetes/checks/policy` already does for every Kubernetes-family addon's own rendering. `infra.kubernetes.policy`/`infra.kubernetes.scan` already apply to a helm target too (`applies_to.addons` names `helm` alongside `kubectl`/`kustomize`) — this pack's own content covers only what is genuinely Helm-specific on top of that, not a second copy of the same rendering-time rules.
