## Jenkins baseline

1. Every job's own agent is pinned to an explicit label — never a bare `agent any` on a shared, multi-tenant controller — so a job never lands on an agent outside its own team's trust boundary. `infra.jenkins.policy`'s own rego enforces this against a real job-config XML target (`jobs/*.xml`); it cannot honestly evaluate a Jenkinsfile or a Job DSL script (see rule 4).
2. A credential is bound only through `withCredentials { ... }`, never read into a shell variable by string interpolation (`sh "curl -H 'Authorization: ${TOKEN}'"` leaks it into the build log and any process on the agent) — `withCredentials`'s own masking applies only when the credential is referenced through the block's own binding.
3. Declarative Pipeline (a `Jenkinsfile`) is preferred over Job DSL (`jobs/*.groovy`) for anything a team maintains directly — Job DSL generates job configuration as a side effect of running Groovy, which is harder to review as a diff than a declarative pipeline's own linear syntax; Job DSL remains the right tool for programmatically generating many similar jobs from one template.
4. `infra.jenkins.policy` (conftest) runs with `input: "render"`, but its own rego only ever fires against a real job-config XML target — a Jenkinsfile's or a Job DSL script's own parsed input carries no comparable structure this pack's own rego can safely evaluate without a real Jenkins server to verify field names and conventions against (the same restraint this addon's own `Drift`/`DryRun` already apply, comparing job-config content as text rather than a structured parse — see `.ai/phase-27/plan.md` §1.2.2). A future phase with real-server access is the right place to extend this rule to the other two shapes, not a guess made here.
