## 1. Toolchain and versions

- **Go version:** the `go` line in `go.mod` is the floor, and it is the newest stable release — today `go 1.27.2`. `go.mod` carries **no `toolchain` line**: a `toolchain` line is redundant when the `go` line already names the newest stable release, and `go mod tidy` removes it. A contributor on an older local Go needs nothing special — `GOTOOLCHAIN=auto`, the default, downloads 1.27.2 on demand from the `go` line.
- **CI pins the toolchain instead of floating it:** `GOTOOLCHAIN=local` plus `actions/setup-go` with `go-version-file: go.mod`, so CI builds with exactly the pinned version rather than auto-downloading. Do not use language or stdlib features newer than the `go` line without bumping it in its own PR first.
- **The bump cadence:** a bump PR within 30 days of each Go release, changing only the `go` line (plus whatever `go mod tidy`/`gofmt -w ./...`/`go fix ./...` produce as a direct consequence). **A feature PR never changes the `go` line.** Only the two latest Go minors receive security fixes, so staying current is not optional.
- Dev tools pinned with the `tool` directive in `go.mod` (`go get -tool ...`): `golangci-lint` (v2; `staticcheck` runs inside it, not as a separate tool), `govulncheck`, `goreleaser` (v2). CI and laptops run `go tool <name>`, never a floating `@latest`.
- The CI gate, in order: `gofmt -l` → `go vet ./...` → `go tool golangci-lint run` → `go test -race -count=1 ./...` → cross-build six platforms (`linux/darwin/windows × amd64/arm64`) with `CGO_ENABLED=0` → `go tool govulncheck ./...` → `go mod tidy && git diff --exit-code go.mod go.sum`.
- `go fix ./...` may be run and its diff committed on its own; never mixed into a feature PR.
